# Contributing to Bottle

Read `AGENTS.md` first. The single source of truth is `research/final-requirements.md`.

## Layout

| Path | What it is |
|---|---|
| `crates/mog-core` | Rust core: secrets, I/O, the IPC gateway (inside the secret boundary). One module per component R1-R14, R16, R17 (section 4.3): a trait plus a `Stub*` type until its feature issue lands. R9 `lakebase_pool` needs the cargo feature `lakebase` (off by default). Only `token_broker` (R6) names the token type. |
| `crates/mog-core-ffi` | C ABI over `mog-core` (R15). The C header `include/mog_core.h` is generated by cbindgen; `BOTTLE_UPDATE_HEADER=1 cargo test -p mog-core-ffi --test header` updates it. |
| `src-tauri` | The Tauri v2 app crate `bottle`. It links `mog-core`. Capabilities per window label are in `src-tauri/capabilities/`. |
| `src/brain` | The hidden brain window: all domain logic (ARC-2). |
| `src/views` | Thin views: hub (V1), MOG (V2), card (V3). |
| `src/shared` | Shared contracts (IPC and interfaces). Only the foundation lead changes them. `interfaces.ts` is the 4.7 contract; its IPC-facing types have a serde mirror in `mog_core::types`. A change to one needs the same change to the other and to `tests/fixtures/ipc-types`. |
| `crates/mog-core/src/local_store/migrations` | Local store schema, forward-only (ADR 0033). A contract path: a change is a new numbered file through a `contract-change` issue. Never edit an applied file. |
| `docs/adr` | Architecture decision records. |

## Branches

- One issue per branch and per PR: `issue/<n>-<slug>`, made from the latest `origin/main`.
- Use one worktree per issue: `../bottle-wt/issue-<n>-<slug>`.
- Never push to `main`. Never force-push `main`. Rebase on `origin/main` before each push.

## Commits

Use Conventional Commits with the issue number: `feat(<area>): ... (#<n>)`, `test(<area>): red for #<n>`, `refactor(...)`, `docs(...)`, `chore(...)`.
End every commit message with a blank line and this trailer:

```text
Co-authored-by: Isaac <no-reply@databricks.com>
```

## The TDD rule

1. Write the failing tests first. Commit them alone as `test(<area>): red for #<n>` and keep the failing output.
2. Write the least code that makes them pass. Commit `feat(<area>): ... (#<n>)`.
3. Refactor with the tests green.

No production code lands without a test that failed first. Paste the red and green output into the PR.

## The test-naming rule

Every test names its requirement IDs, so the coverage script can map tests to requirements:

- TypeScript: `it('[CAP-14b] stops hands-free on Esc', ...)`
- Rust: `#[test] fn cap_14b_stops_on_esc()` (the ID in lower case with `_`)
- Python: `def test_nfr_23a_...` with `[NFR-23a]` in the docstring
- Acceptance tests: `[AT-07]`

A test that names an ID that does not exist in `research/final-requirements.md` fails the coverage check.

## Run the checks locally

Prerequisites: Rust stable with `clippy` and `rustfmt`, Node 22 or later, pnpm 11, uv.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test                       # Vitest; pnpm test:ci writes reports/junit-ts.xml and coverage
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo nextest run --workspace --locked --profile ci   # CI form; writes target/nextest/ci/junit.xml
pnpm tauri build --debug        # macOS or Windows app bundle
uv run --no-project --with pytest --with pyyaml pytest scripts/tests -q   # when scripts/tests exists
```

App CI has no macOS runner (ADR 0045). On a Mac, run `scripts/pre-push.sh` before every push, and paste its summary into the PR. The script is the macOS gate: it runs the CI checks, the pinned cargo-nextest check, requirement coverage, the offline build (AT-37) and the golden set (SEC-26). A macOS-only break is caught only by this script. To run it on each `git push`, install it as the pre-push hook:

```sh
ln -sf ../../scripts/pre-push.sh "$(git rev-parse --git-common-dir)/hooks/pre-push"
```

CI runs these commands on Windows (`windows-2025`) and Linux (`ubuntu-24.04`) for each PR, on push to main, nightly and on dispatch, in `.github/workflows/app-ci.yml`. It also builds offline from the lockfiles (AT-37) and packages an unsigned debug NSIS installer with a SHA-256 file. The Windows signing step runs only when the `WINDOWS_*` secrets exist. On a Mac, `scripts/package-macos.sh` builds the DMG and its SHA-256 file. It signs and notarizes the DMG only when the `APPLE_*` secrets exist (NFR-15a).

## Pull requests and the merge gate

- Use `.github/pull_request_template.md`. Fill every heading.
- An independent reviewer agent posts a PR comment whose first line is `REVIEW: APPROVED` or `REVIEW: CHANGES REQUESTED`.
- Merge only with all CI checks green and `REVIEW: APPROVED`. Squash merge and delete the branch.

## Names in UI text

- The product name is "Bottle". Do not use the former names of the app in UI text or package metadata (MB-10a).
- The hub title bar and the About screen show "Databricks Labs / experimental" (MB-10b).
- "MOG" is a UI noun only. Write "MOG" or "MOGs" in UI text, never "mog" or "Mog" (MB-10c).
- Do not put "mog" in a package ID or a bundle ID. Code names such as `mog-core` and `mog-<id>` are not UI text.
- `pnpm test` (`src/acceptance/at-37-naming.test.tsx`) and `uv run --no-project python tools/ci_checks.py names` check these rules. ADR 0030 gives the scope.

## Third-party code and licences

- When you add, port or adapt third-party code, update `THIRD_PARTY_NOTICES.md` in the same PR.
- Follow the "How to add an entry" steps at the top of that file.
- The About screen shows the file text. `pnpm test` checks the notices and the file headers (SEC-21a, SEC-21b).

## Never commit

Secrets, `.databrickscfg`, `.env*`, `*.pem`, `*.key`, `build/`, `*.riv`. Tokens come only from `databricks auth token --profile <p>` at run time.
