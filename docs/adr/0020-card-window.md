# ADR 0020: The card window: key-capable panel, lazy create, reaper and Esc

- Status: Accepted
- Date: 2026-11-16
- Issue: #78 (depends on #11, ADR 0009; extends #8, ADR 0008)
- Owner: shell-lead (implemented by impl-78)

## Context

MOG-03a, MOG-03b, MOG-18a, MOG-18b, UX-19a and UX-19b need each `card-<id>` window to be a key-capable non-activating panel at Floating level. It must keep the frontmost app, be made on the first open and be destroyed after 5 min hidden. It must be the only window that takes the keyboard, and Esc must close the card or cancel the request with no half state. The issue left five points open. The PR #292 review (LOW) also asked for two ledger fixes in the card reaper.

## Decisions

1. **A second panel class, same seam.** `src-tauri/src/macos_panel.rs` adds `BottleCardPanel`, an `NSPanel` subclass with `canBecomeKeyWindow = true` and `canBecomeMainWindow = false`. `WindowKind::Card.panel()` gives Floating level, `NSWindowStyleMaskNonactivatingPanel`, `hidesOnDeactivate = false`, and the MOG collection behavior. `apply_panel` picks the class from `can_become_key`. It uses the same class swap and content-view swap around WebKit KVO as ADR 0009. The tauri-nspanel #104 behavior (a non-activating panel that becomes key) comes from the style mask plus `canBecomeKeyWindow`. Bottle does not use the crate (ADR 0009, decision 1). `apply_panel` refuses a main-capable spec. It also refuses to turn a MOG panel into a card panel or back, so a MOG panel never becomes key (UX-19a). The card is not transparent (`PanelSpec::transparent = false`), so the step keeps its opacity and shadow.
2. **Show without activation.** The card is built hidden and not focused. `MacPanelStyle::show` calls `orderFrontRegardless`, then `makeKeyWindow`, then makes the WKWebView the first responder (`focus_web_view`). No code path calls `activate`, `activateIgnoringOtherApps`, `makeKeyAndOrderFront` or Tauri `set_focus` (test `mog_03b_macos_panel_code_never_activates_bottle`). A non-activating key panel gets the keys and the IME while the frontmost app stays (MOG-03b). The card panel class is not in the MOG drag monitor, so a card is never dragged.
3. **UX-19a scope.** "The only surface that takes keyboard focus" applies to the floating surfaces: the MOG panels, their chips and the card. The hub is the normal app window that the user opens from the Dock, and it takes focus as any app window does. The brain window is never focusable. The test `ux_19a_only_the_card_panel_can_become_key` checks this.
4. **Card states and the reaper.** The R11 ledger keeps one `CardState` per open MOG: `Absent` (no WebView), `Shown`, `Hidden(since)` and `Closing`. `show_card` makes the window only from `Absent` (MOG-18a). `hide_card` marks the card hidden only after the window hid. A second hide keeps the first time, and a show resets it. `spawn_card_reaper` runs a thread that calls `reap_hidden_cards` every `CARD_REAP_TICK` (15 s). A card hidden for `CARD_HIDDEN_TTL` (5 min) or more is destroyed between 5:00 and 5:15 after its hide (MOG-18b). The time source is injected, so the tests use a fake clock.
5. **Closing windows (PR #292 review).** When the host destroys a window, the label waits for its `Destroyed` event (`expect_destroyed`). Until the event comes, an open or show of that label gets `WindowError::Closing` (code `window_closing`). So a late `Destroyed` event of an old window cannot free the slot of a new window with the same label. A new window also never adopts the dying one, because `windows::build` returns an existing window with the same label. A MOG window that closes outside the host now also destroys its card.
6. **Esc.** The card view listens for `keydown` on its window, because the card is the key window and the focus can be on any element in it. One Esc press sends one `view_emit` `cancel`. A key repeat sends nothing more. An Esc during IME composition (`isComposing` or key code 229) only ends the composition (MOG-03a). The brain rule `src/brain/card-esc.ts` does exactly one action per Esc. A request in flight is cancelled and the card stays, so it can show "cancellation requested". With no request in flight the card hides. A failed action is not followed by the other one (UX-19b). The brain cannot call `window_card_hide` through the gateway yet (`TODO(#285)`), so the rule is built and tested behind a dependency interface.

## Consequences

- A person checks on a Mac that 20 card opens keep the frontmost app, that the card is the key window, that typing and the IME work, and that the card WebView goes after 5 min hidden. The script is `tools/mac/card-check.swift`. The steps are on #336 (`needs:human`, `needs:mac`, `TODO(#336)`). Debug builds have `BOTTLE_DEMO_CARD_CYCLE=1` (20 hide and show steps of the demo card) and a "Typing probe" field in the demo card only (`import.meta.env.DEV`).
- Windows: the card shows through `PlainStyle` and can take the foreground (`TODO(#80)`, `WS_EX_NOACTIVATE`).
- A show of a card in the few milliseconds while its old WebView closes gets `window_closing`. The brain retries after the next `Destroyed` event once #285 routes the window commands.
