## 2. Method

1. A standalone throwaway Tauri v2 app in `spikes/sp-01/` (its own `[workspace]`, not in any app skeleton). It has one window, `mog-spike`. The flags are `transparent: true`, `decorations: false`, `alwaysOnTop: true`, `focus: false`, `shadow: false` and `skipTaskbar: true`. The setup code calls `set_focusable(false)` and sets the activation policy to `Accessory`. Then it applies the objc2 overlay step (`src-tauri/src/main.rs::macos_overlay`): clear background, not opaque, no shadow, `canJoinAllSpaces | fullScreenAuxiliary | stationary`, `acceptsMouseMovedEvents`, and `orderFrontRegardless` (show without activation). On `RunEvent::Ready` and after each focus sample it calls `NSApp.deactivate()`. `macOSPrivateApi` is NOT set.
2. The CSP is exactly ARC-4: `default-src 'self'; connect-src ipc: http://ipc.localhost; script-src 'self' 'wasm-unsafe-eval'`. Rive cannot `fetch` its wasm under this CSP, so the page gets the wasm and the `.riv` as bytes over IPC (`sp01_blob`) and calls `RuntimeLoader.setWasmBinary`. `enableRiveAssetCDN: false`.
3. The page (`web/`) loads ONE runtime per run: `@rive-app/webgl2` 2.50.0 or `@rive-app/canvas` 2.50.0. It lists the state machines, inputs and view-model properties. If `mood`/`level` exist, it cycles the 7 moods and the level. Otherwise it loops the timeline animations. It logs `pointermove`, `pointerenter` and `mouseover` (capture phase) with page timestamps to Rust (`sp01_log`). Rust adds its receive time and writes JSONL.
4. `probe-swift/PostMoves.swift` posts `CGEvent` mouse moves at the HID tap into the window rect, 200 per burst at 10 ms intervals, 3 bursts per case. It records `AXIsProcessTrusted()` and the cursor position after the last move.
5. `probe-swift/Probe.swift` is a **WKWebView + NSPanel probe, not Tauri**. It is a borderless `.nonactivatingPanel` with a WKWebView (`drawsBackground=false`) and the same page and CSP. It answers two questions that the Tauri build cannot answer here: the alpha of the WebView output (`takeSnapshot`, offscreen), and whether an extra native tracking area fixes hover.
6. `run_measurements.sh` runs the whole case matrix ONCE: small 240 px windows, 20 px in from the bottom-right corner. It closes each window when its case ends. CPU and memory come from `top -l 31 -s 1 -stats pid,cpu,mem` over the app PID plus the WebKit PIDs that the launch made (WebContent, GPU, Networking). The first sample is dropped and the sum per sample is averaged over 30 samples.
7. `measure/sp01_measure.py` computes CIEDE2000 (checked against the Sharma 2005 reference pairs), transparency stats over non-sprite pixels, halo (light ring pixels just outside the sprite), white flash, hover ratio and the `top` sums. Tests: `uv run --no-project --with pytest --with pillow pytest spikes/sp-01/measure -q`.

## 6. Findings

1. **Hover does not arrive in a non-key window (COL-71 risk is real).** WebKit sends no DOM pointer events to the page while the window is not key: 0 of 600 moves for Tauri webgl2 and Tauri canvas, and 0 of 600 for the NSPanel probe. With a key, focusable window (control), the same poster gave 94/100 and 98/100 `pointermove`. In the exploratory probe runs, 2 of 14 non-key runs got some events (48 of 100, 41 of 200); the other 12 got 0. Delivery in a non-key window is therefore at best unreliable.
2. **An extra NSTrackingArea did not fix it.** The probe added an always-active tracking area with the WKWebView as owner (`SP01_TRACK=1`), and an always-active tracking area with a native owner that forwards into the page as synthetic `PointerEvent`s (`SP01_TRACK=2`). Both got 0 events in the matrix run. The native owner logged 0 `mouseMoved:` calls. So AppKit did not send mouse moves to the window at all while it was not key, and the fix must not depend on `mouseMoved:` events.
3. **Activation is not stable.** `focus:false` + `set_focusable(false)` + `Accessory` + `orderFrontRegardless` kept the window from becoming key in every sample. But the app itself became active (`NSApp.isActive=true`, and `lsappinfo front` showed the spike) in 16 of 18 launches. In the first 2 launches it stayed inactive. `NSApp.deactivate()` on `RunEvent::Ready` and after each sample did not hold. This matches tao's launch-time activation together with macOS 14+ cooperative activation (the grant depends on what the user does at that moment). ARC-3 needs a launch path that never asks for activation.
4. **Transparency without `macOSPrivateApi` holds in the WebView layer.** The WKWebView with `drawsBackground=false` gives alpha 0 outside the artboard and alpha 255 inside, with 0 partial-alpha pixels, for both runtimes. Over the 16 px checker, Delta E max is 0.00 on 98,880 pixels, with 0 halo pixels. This does not prove the window-server composite or the signed-DMG case (Tauri #13415). Those need Screen Recording and the signed rerun.
5. **Offscreen windows do not animate.** At x=-3000, WebKit throttles `requestAnimationFrame` to 0 frames in 5 s, and snapshots at 2.0/2.5/3.0 s are byte-identical. Offscreen numbers are therefore valid for alpha only, not for flash timing or animation.
6. **The ARC-4 CSP blocks Rive's default wasm `fetch`.** The app must pass the wasm bytes (`RuntimeLoader.setWasmBinary`) and the `.riv` bytes (`buffer:`) over IPC, or ARC-4 must allow `connect-src 'self'`. The spike uses IPC bytes; this works for both runtimes.

## 7. Recommendation

**Provisional: `@rive-app/canvas`** (NFR-16a). Confirm it in the signed rerun with the MOG mascot.

Evidence:
- Both runtimes give the same WebView alpha (0 partial-alpha pixels, Delta E 0.00) under the ARC-4 CSP. Transparency does not decide the runtime.
- Memory: canvas used less in every valid case. Idle: 111.7 MB against 130.3 MB. No-motion run1: about 102 MB against about 131 MB.
- The only webgl2 animating sample is invalid: the page stalled for about 34 s after launch. canvas animated at 60 fps from the start in all 4 canvas runs. One stall is not proof of a webgl2 fault, but it is the only render problem seen.
- canvas animating cost 11.3 % CPU (summed over 4 processes) on a heavily loaded M3 Max. This needs a check against the NFR CPU budget on an M1 with the real mascot.

**`macOSPrivateApi` needed: NO** in this unsigned run. The transparency evidence is in the WebView layer only. The signed DMG case (Tauri #13415) is NOT RUN. `macOSPrivateApi` also does not change how AppKit routes mouse moves to a non-key window, so it would not fix the hover failure.

**Fallback chain reached (D73 / SP-01):**
1. `canvas` runtime: tried. Same result as webgl2 for hover (0/600) and transparency (pass in the WebView layer).
2. Own `objc2` fix: tried. The overlay step plus `deactivate()` did not keep the app inactive. Two NSTrackingArea fixes (WKWebView owner, and a native owner that forwards to the page) got 0 events. FAIL for hover and activation.
3. `macOSPrivateApi: true`: NOT TRIED. It targets transparency, which did not fail here, and it does not affect key-window event routing.
4. Static WebP poster: not needed for rendering. It does not fix hover.

Hover needs a source that does not depend on the window being key. Candidates: poll `NSEvent.mouseLocation` in the Rust core at 60 Hz and send hover-in/out to the MOG view, or use a listen-only `CGEventTap` (needs Input Monitoring). Either way the page gets host events, not native DOM events. This changes the UX-08a acceptance.

## 8. Signed rerun (needs:human, needs:mac): under 30 minutes per Mac

Script: `spikes/sp-01/sign_and_rerun.sh`. Run it once on an M1 with macOS 14.4 and once on the current macOS.

1. (2 min) Install Xcode command line tools, Rust stable, Node 22+, pnpm, uv and the `rive` CLI. Clone the repo and check out the branch `issue/10-sp01-rive-transparent`.
2. (3 min) Grant the terminal: Privacy & Security > Screen & System Audio Recording, and Privacy & Security > Accessibility. Restart the terminal.
3. (3 min) Build the mascot: `cp -R mog-rive /tmp/mog-rive && cd /tmp/mog-rive && rive login && rive . --publish`. The `.riv` goes to `/tmp/mog-rive/build/`. Do not commit it.
4. (2 min) Make the notary profile once: `xcrun notarytool store-credentials <your-profile> --apple-id <apple-id> --team-id <team-id>`.
5. (15 min, mostly notarization) Run:
   `APPLE_SIGNING_IDENTITY="Developer ID Application: <name> (<team>)" NOTARY_PROFILE=<your-profile> SP01_RIV=/tmp/mog-rive/build/mog-rive.riv spikes/sp-01/sign_and_rerun.sh`
6. (5 min) Fullscreen Space: put any app in full screen, then run `OUT=/tmp/sp01-fs spikes/sp-01/run_measurements.sh "/Applications/SP01 Rive Transparent.app" "$SP01_RIV"` while that Space shows. Record whether the mog shows on that Space. Screen share: start a Zoom, Meet or QuickTime screen recording of the full display. Record whether the mog shows, and with what background.

Expected output: `notary.txt` has `status: Accepted`. `spctl-app.txt` has `accepted` and `source=Notarized Developer ID`. The script prints one line per result file (`front-*`, `hover-*`, `cpu-*`, `snap-*`, `screen-*`).

Pass rule (all must hold on both Macs):
- `screen-*/transparency.json`: `"pass": true` (every transparent pixel Delta E < 2) and halo `"halo_px": 0`.
- `screen-*/flash.json`: `"white_flash_ms"` <= 100.
- `hover-tauri-*.json`: `"pass": true` (received / sent >= 0.9).
- `front-tauri-*.json`: `front_1s` and `front_end` equal `front_before`, and the log has `"is_key":false` and `"app_active":false`.
- The run log shows all 7 moods and the level change (`"msg":"anim"` lines).
- Fullscreen Space and screen share: the mog shows with a transparent background.
