## Method

`sp03-probe` is a CLI. It opens no window. It has four commands:

| Command | What it does | Prompts? |
|---|---|---|
| `status` | Prints `CGPreflightListenEventAccess`, `CGPreflightPostEventAccess`, `AXIsProcessTrusted`, `IsSecureEventInputEnabled` (and the holder from `ioreg`), `AppleClamshellState` (IOKit and `ioreg`), the physical Right Option state and the CGEvent clock. | Never |
| `listen` | (a) A listen-only `CGEventTap` (`kCGEventTapOptionListenOnly`, session tap) runs on its own run-loop thread. It logs the talk key Right Option (`kVK_RightOption` 61, D66 default; it comes as `kCGEventFlagsChanged`) down and up, with the latency from `CGEventGetTimestamp` to the callback. When the OS disables the tap, the probe enables it again and counts it (CAP-38a). (b) A thread polls `IsSecureEventInputEnabled()` every 10 ms. It logs SEI on and off, and the time from the SEI-on detection to "PTT ended". (c) It registers the Carbon `RegisterEventHotKey` chord Ctrl+Shift+Space and logs `kEventHotKeyPressed` and `kEventHotKeyReleased`, with the latency from `GetEventTime`. (d) A thread polls `AppleClamshellState` of `IOPMrootDomain` every 200 ms and logs lid close and open. | Only with `--request-access`: it calls `CGRequestListenEventAccess`. Without Input Monitoring and without that flag, the tap is skipped, so no prompt can appear by accident. |
| `self-test` | Posts N synthetic Right Option down/up pairs (`CGEventPost` at the HID tap, tagged in `kCGEventSourceUserData`). It measures delivery and latency at its own listen-only tap. It runs only if the preflight shows both listen and post access. Otherwise it prints `BLOCKED` and the missing permission. | Never |
| `analyze <log>` | Pairs the `EV` lines of a `listen` log: downs, ups, pairs, missed key-ups, orphan key-ups, key-up percent, latency p50/p95. Runs on every OS. | n/a |

- **PTT state machine** (`sp03::Ptt`, CAP-39a/b): the talk key starts and ends PTT. When SEI turns on, an
  active PTT ends with `reason=SecureInput`. While SEI is on, the talk key is ignored and the chord drives PTT.
  When SEI turns off, the talk key works again, and the probe reads the physical Right Option state (CAP-45).
- **Missed key-up**: a key-down with no key-up before the next key-down, or a key-down at the end of the log.
- **Event clock**: `CGEventCreate` stamps events in `mach_absolute_time` ticks, but posted events carry
  nanoseconds of `CLOCK_UPTIME_RAW` (seen in the raw `ts_raw` values). `event_latency_ns` reads both clocks
  and picks the one where the age is not negative and less than 10 s.
- **SEI holder**: the slow `ioreg -l` lookup of the holder runs on its own thread, not on the 10 ms poll thread.
- **Privacy**: the probe logs only the talk key and the chord. It counts other key events by type only. It never
  reads or logs which other key was pressed.
- **Handy (reuse)**: adapted from cjpais/Handy @ aca8985 (MIT), one Bottle file per Handy file:
  `spikes/sp-03/src/secure_input.rs` (from `src-tauri/src/secure_input.rs`: the `IsSecureEventInputEnabled`
  binding and the `ioreg` lookup of the SEI holder) and `spikes/sp-03/src/clamshell.rs` (from
  `src-tauri/src/helpers/clamshell.rs`: the `ioreg` lid check, a cross-check of the IOKit read). Handy also
  states that while SEI is on, a tap gets no KeyDown/KeyUp but still gets FlagsChanged. Right Option is
  modifier-only, so step S1 records whether its key-up still comes under SEI.

The first 50-pair run had a clock bug: every latency was 0, because posted events use nanoseconds. Its delivery
was the same (100 of 100). I fixed the bug with a test (`sp_03_nfr_08b_event_latency_picks_the_clock_that_fits`),
checked the fix with 5 pairs, and ran the 50 pairs again (above). In total the probe posted 105 synthetic pairs
in about 5 s.

## Person steps: NOT RUN

The steps are in three sessions. Each session takes 30 min or less. The Windows part comes when the Windows probe
exists.

| Session | Steps | Time |
|---|---|---|
| 1 | Set-up, Pico rig, H1 Safari, H2 Terminal, H3 VS Code | about 28 min |
| 2 | H4 Zoom, H5 Word, P0 permission prompt | about 20 min |
| 3 | S1-S5 (Secure Event Input and the chord), L1-L2 (lid) | about 25 min |

What the latency covers (NFR-08b): the probe measures from the CGEvent timestamp to the tap callback. The OS
sets the timestamp when the HID event enters the event system. So the number does not include the USB poll
interval of the Pico (the `bInterval` of its HID endpoint, often 1-10 ms) or the HID driver time before the
timestamp. Record the measured p95 and this gap together.

### Session 1 (about 28 min)

#### Set-up (macOS, about 3 min)

```sh
export PATH="$HOME/.cargo/bin:$PATH"
cd spikes/sp-03 && cargo build --release
./target/release/sp03-probe status
```

Expected: four `STATUS` lines, for example `STATUS secure_input=0 holder=-` and `STATUS lid_iokit=open ...`.

#### Pico rig (Raspberry Pi Pico, about 5 min)

`code.py` starts a 1,000-cycle run 10 s after each boot. A boot also happens when CircuitPython reloads after
you copy `code.py`. So:

1. Put a wire from GP14 to GND (abort) before you copy anything. Then a reload cannot start a run.
2. Hold BOOTSEL and plug in the Pico. Copy the CircuitPython 9.x UF2 for the Pico to `RPI-RP2`.
3. Copy `adafruit_hid` from the Adafruit CircuitPython bundle to `CIRCUITPY/lib/` (or run `circup install adafruit_hid`).
4. Copy `spikes/sp-03/pico/code.py` to `CIRCUITPY/code.py`.
5. Unplug the Pico. If you did not use the GP14 wire, unplug it within 10 s of step 4.
6. Remove the GP14 wire. Plug the Pico in once with no app open that takes text, and unplug it within 10 s
   (or ground GP14 again). macOS sees the new keyboard. If it shows the "Keyboard Setup Assistant", close it.
   Do this before H1, so the assistant cannot take the focus during H1.
7. Optional: a wire from GP15 to GND starts a run at once.

The Pico is a USB keyboard. It presses Right Alt (Right Option on macOS) 1,000 times: hold 50-150 ms, gap
100-200 ms, fixed seed. It starts 10 s after you plug it in. One run takes about 4.5 min. Its serial console
prints `CYCLE n` lines and `DONE cycles=1000 of 1000`.

#### H1-H3 (about 20 min; H4-H5 are in session 2)

For each app: start the probe, put the app in front with a document or page open, then plug in the Pico within
20 s. Do not touch the keyboard during the run. Watch the app: Right Option alone must not open a menu, move the
focus or type a character. Unplug the Pico after `DONE`.

```sh
./target/release/sp03-probe listen --seconds 360 --no-carbon | tee h1-safari.log
./target/release/sp03-probe analyze h1-safari.log
```

The run is 360 s: 10 s start delay, about 250 s of cycles, and time to plug in. If the probe stops before the
Pico prints `DONE`, the log is cut and shows missed key-ups. Run that app again.

`ANALYZE src=tap downs=1000 ups=1000 pairs=1000 missed_key_ups=0 orphan_key_ups=0 key_up_percent=100.000 latency_ms[n=2000 ... p95=<= 15 ...]`.
The Pico must print `DONE cycles=1000 of 1000`.

### W1-W3: Windows 11 (TODO(#5))

There is no Windows probe yet: `run_platform` on Windows prints a message and exits 2. Only `analyze` runs.
The crate is cfg-clean for `x86_64-pc-windows-msvc` (`cargo clippy --target x86_64-pc-windows-msvc` passes on
the Mac).

Design note for the Windows probe:
- Primary: `WH_KEYBOARD_LL` on a dedicated thread with its own message loop (CAP-40a). It logs `VK_RMENU`
  (0xA5) down and up with `KBDLLHOOKSTRUCT.time` against `GetTickCount`, and it swallows the talk key
  during capture so the menu bar does not activate (CAP-41).
- Fallback: Raw Input with `RegisterRawInputDevices` (usage page 1, usage 6, `RIDEV_INPUTSINK`) on a
  message-only window (`HWND_MESSAGE`, never visible). Plus a toggle chord through `RegisterHotKey`.
- Known gap to measure: UIPI. A medium-integrity hook gets no events while an elevated window is in front.
  That is why CAP-42 shows a tooltip.

## Pass rule

SP-03 passes when all of these hold:

1. H1-H5: 1,000 of 1,000 key-ups in each app, `missed_key_ups=0`, p95 ≤ 15 ms, and no menu activation.
2. P0: only the Input Monitoring prompt appears.
3. S1: in each try, `upper_bound_sei_to_end_ms` ≤ 250. S2: 10 of 10 chord presses and releases.
4. L1: lid close and lid open are logged.
5. Windows W1-W3 pass (needs the Windows probe).

## Fallback

- macOS, if the listen-only tap misses key-ups or SEI blocks it: an active tap (`kCGEventTapOptionDefault`)
  with Accessibility, or the Carbon chord only.
- Windows, if `WH_KEYBOARD_LL` fails (for example with an elevated window in front): Raw Input
  `RIDEV_INPUTSINK` plus a toggle chord.

## Follow-ups

1. **Windows probe** (`TODO(#5)`): build the `WH_KEYBOARD_LL` and Raw Input probe from the design note, then run
   W1-W3. Open a follow-up issue for it.
2. **Event clock**: CGEvent timestamps use ticks or nanoseconds depending on the source. HotkeyService must not
   assume one clock. Use the same rule as `event_latency_ns`, with a test.
3. **Carbon delivery in a CLI**: if S2 fails in the probe, repeat S2 in the app bundle before choosing the fallback.
4. **SEI and FlagsChanged**: if S1 shows that the Right Option key-up still arrives under SEI, record it in
   CAP-39a/b. PTT must still end on SEI (CAP-39a), but this lowers the risk of a stuck PTT.
5. **Tap watchdog** (CAP-38a): the probe enables the tap again on `kCGEventTapDisabledByTimeout`. No run here
   caused a timeout (`tap_disabled=0`). A test that forces a slow callback belongs to the HotkeyService issue.
