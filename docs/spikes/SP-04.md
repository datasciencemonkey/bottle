# SP-04: local Parakeet STT latency (issue #44)

**Status: PARTIAL.** This run used an Apple M3 Max, which is not reference hardware. The reference
hardware is an M1 Mac, an M2 Mac, and an i5-1235U or Ryzen 5 7530U Windows laptop. A person must
run `spikes/sp-04/run.sh` (Mac) and `spikes/sp-04/run.ps1` (Windows) on that hardware to close the
spike (see "Rerun on reference hardware").

Requirements: SP-04 (section 16), CAP-48, CAP-50a, CAP-51c, CAP-52, NFR-05, section 8.1 step 3,
section 8.3.

## Result on M3 Max (PARTIAL, not reference hardware)

Canonical run: threads = 12 (the P-core count, CAP-48), 20 timed runs after 3 warm-up runs,
host load average 23-24 (see "Environment").

| Criterion (SP-04) | Limit | M3 Max value | Result on M3 Max |
|---|---|---|---|
| 10 s clip p95 | <= 600 ms (M1), <= 900 ms (Windows) | 593.1 ms | PASS (barely, under shared load) |
| Tail p95 (3 s tail + 120 ms post-roll) | <= 400 ms | 232.6 ms | **CONDITIONAL** PASS (see below, #283) |
| Tail p95 if the tail is the whole utterance (10 s) | <= 400 ms | 593.1 ms | FAIL |
| Peak RSS (NFR-05) | <= 1.0 GB | 1.91 GB (`/usr/bin/time -l`: 1,910,472,704 B) | **FAIL** |
| Model load, fresh process | <= 3 s | 815-872 ms (5 runs) | PASS |

The RSS failure does not depend on CPU speed: RSS is already 1.18 GB right after the model loads,
and it goes to 1.9 GB after the first 30 s decode. Expect the same failure on M1, M2 and Windows.
The fallback chain and the follow-ups below address it (#282).

**The tail result is CONDITIONAL.** It is a PASS only if the PTT VAD closes segments at pauses
during the hold, so that the tail after key-up is 3 s or less. The requirements do not set that rule
yet (#283). CAP-52 already says that SttEngine decodes closed VAD segments during speech and that
only the tail decodes after key-up, but no requirement sets the PTT segment length. The only segment
rule today is R2 / CAP-19a: 15-20 s target, 30 s hard. With that rule, a PTT utterance of 15 s or
less has no closed segment before key-up. The tail is then the whole utterance, and the 10 s p95
(593.1 ms) is over the 400 ms tail limit.

## Method

- Benchmark crate: `spikes/sp-04/` (own `[workspace]`, committed `Cargo.lock`, not part of the app).
  `src/lib.rs` has the WAV reader, percentiles, WER, tail split, peak RSS and the `Engine` wrapper.
  `src/main.rs` is the `sp04-bench` binary.
- Engine: `sherpa_onnx::OfflineRecognizer` with `OfflineTransducerModelConfig`
  (`encoder.int8.onnx`, `decoder.int8.onnx`, `joiner.int8.onnx`), `tokens.txt`,
  `model_type = "nemo_transducer"`, `provider = "cpu"`, `decoding_method = "greedy_search"`,
  `num_threads` = the P-core count (`hw.perflevel0.physicalcpu` on macOS; `--threads` on Windows).
- Latency of one decode = create stream + accept waveform + decode + get result, in one process
  with the model warm (CAP-51c preloads the model at key-down, so the load is not in this number).
  Each clip has 3 warm-up decodes and then 20 timed decodes. Percentiles use the nearest-rank
  method (`sp_04_percentiles_correct`).
- Clips: macOS `say -v Samantha -r <rate> --data-format=LEI16@16000` (16 kHz, 16-bit, mono WAV).
  The bench pads each clip with trailing silence to exactly 2, 5, 10 or 30 s (the 10 s clip is
  10.02 s and is not cut). Speech lengths: 1.83, 4.26, 10.02 and 28.26 s. The clips and the
  reference texts stay in `/tmp` (not committed). `run.sh` holds the texts and rates, and `say`
  output was byte-identical between two runs on this Mac.
- Rough WER: word-level Levenshtein distance after lower-case and punctuation removal.
- **Tail latency (interpretation of 8.1 step 3 and CAP-52):** during speech, SttEngine decodes each
  closed VAD segment. At key-up, only the open tail segment is left to decode. The bench takes the
  last T s of the speech (T = 1, 2, 3, 5), adds the 120 ms post-roll of 8.1 step 1 as silence,
  decodes the segment just before the tail (up to 5 s, untimed, as the app does just before key-up),
  and then times only the tail decode. The pass check uses T = 3 s. This is an assumption about
  the PTT VAD segment length, which the requirements do not set yet (#283). The 1, 2 and 5 s rows
  show the sensitivity. If no segment closes before key-up (a user who speaks with no pause, or a
  VAD with the R2 15-20 s target), the tail is the whole utterance: the full-clip rows give that
  case, and the bench prints it as an informational row.
- Clip length check: the bench prints a WARNING and ends with `SP04_RESULT INVALID` (exit 2) when
  a clip is more than 0.2 s longer than its nominal length (`sp_04_clip_length_check_flags_long_clips`).
  On this Mac every clip is within the limit (the longest is the 10 s clip at 10.02 s).
- Peak RSS: in-process `getrusage(RUSAGE_SELF).ru_maxrss` (macOS reports bytes) or
  `GetProcessMemoryInfo.PeakWorkingSetSize` on Windows, plus `/usr/bin/time -l` on macOS. NFR-05
  asks for a 4 min clip: the bench also decodes a 240 s stream (the 30 s clip 8 times) in 20 s
  segments, as the session VAD does (CAP-19a).
- Load: `sp04-bench load` in 5 fresh processes, time of `OfflineRecognizer::create`.
  Cold file cache: `sudo purge` needs a password on this Mac (`sudo: a password is required`), so
  the cold-cache load is not measured here. All loads here have a warm OS file cache.
  `SP04_PURGE=1 bash spikes/sp-04/run.sh` measures it on the reference Macs.
- Real-time factor (RTF) = decode time / audio length.

- 10 s p95 <= 600 ms: **PASS** (593.1 ms, very close to the limit, under shared load).
- Tail p95 <= 400 ms: **CONDITIONAL PASS** (232.6 ms for a 3 s tail; 350.7 ms for a 5 s tail).

- RSS <= 1.0 GB: **FAIL** (1.91 GB peak; 1.18 GB right after load).
- Load <= 3 s: **PASS** (815-872 ms, warm file cache; the cold cache was not measured).
- Overall: **PARTIAL** (not reference hardware). The RSS criterion fails on this machine, and the
  tail result depends on #283.

## Rerun on reference hardware (under 30 minutes)

Run each script on AC power, with other apps closed. The scripts download 0.51 GB (Mac: model
487 MB + libs 21 MB) or 0.61 GB (Windows: model 487 MB + libs 123 MB), check every SHA-256, build,
run the model test and run the benchmarks.

**M1 Mac and M2 Mac** (Rust stable 1.88 or later: `curl https://sh.rustup.rs -sSf | sh`):

```bash
git clone https://github.com/datasciencemonkey/bottle && cd bottle
SP04_PURGE=1 bash spikes/sp-04/run.sh 2>&1 | tee ~/sp04-$(sysctl -n hw.model).log; echo "run.sh exit=${PIPESTATUS[0]}"
```

`SP04_PURGE=1` asks for your password once (`sudo purge`) to measure a cold-cache load. Leave it out
to skip that step. Approximate time: download 2-5 min, build 1-3 min, benchmarks 6-12 min.

**Windows laptop (i5-1235U or Ryzen 5 7530U)**: install Rust (rustup, MSVC toolchain) and Visual
Studio Build Tools with "Desktop development with C++". Then in PowerShell:

```powershell
git clone https://github.com/datasciencemonkey/bottle; cd bottle
powershell -ExecutionPolicy Bypass -File spikes\sp-04\run.ps1
```

The script sets threads = 2 for the i5-1235U (2 P-cores) and 6 for the Ryzen 5 7530U. For another
CPU, pass `-Threads <P-core count>`. For the same audio as the Macs, copy `~/sp04-work/audio` from
a Mac run and pass `-AudioDir <folder>`. Otherwise the script makes the clips with System.Speech.
If the link step fails with `LNK2038` (CRT mismatch with the MT-built libraries), set
`$env:RUSTFLAGS="-C target-feature=+crt-static"` and run the script again. Record that in the
issue. This Windows path is not tested yet (no Windows machine in this run). The script works in
Windows PowerShell 5.1 and in PowerShell 7. It keeps `$ErrorActionPreference = "Continue"` so that
stderr progress lines from `curl.exe`, `cargo` and `tar.exe` do not stop it, and it checks
`$LASTEXITCODE` after each native command. It writes its own log with `Start-Transcript`
(`~/sp04-work/out/run-ps1.log`), so do not redirect its output with `*>&1`. Windows PowerShell 5.1
may leave cargo's output out of the transcript; the files `load.txt`, `bench-p.txt` and
`bench-all.txt` hold the results in all cases.

## Fallback chain (section 8.3, SP-04 row)

If a reference machine fails a criterion, use the next step in this order:

1. Databricks ASR, opt-in, only after its probe passes (SP-05; CAP-57c, CAP-57e). Local Parakeet
   stays the default and the fallback for cloud ASR failures (8.3).
2. FluidAudio on the Apple Neural Engine (v1, macOS only).
3. NeMo GGUF build of Parakeet.
4. Moonshine v2 (English only).

The RSS failure is not a latency failure, so first try the RSS follow-ups below before a switch.
A switch to cloud ASR does not fix PTT for `SttPolicy=local_only` users.

## Follow-ups

1. **NFR-05 vs measured RSS (blocker for NFR-05), #282:** measure RSS with smaller decode segments
   (for example 10 s), onnxruntime session options that the C API does not expose today (arena off,
   memory pattern off), and the fp32 encoder with external weights mapped from disk. If none gets
   to 1.0 GB, propose a change to NFR-05 (for example 2.0 GB) or a fallback step. Owner: spike-lead.
2. **Reference hardware rerun:** run `run.sh` on M1 and M2 and `run.ps1` on the Windows laptop
   (needs a person and devices: `needs:human`, `needs:mac`, `needs:windows`).
3. **Cold-cache load:** measure with `SP04_PURGE=1` on the reference Macs (needs sudo).
4. **Windows build:** confirm that the MT-built static libraries link with the default Rust MSVC
   CRT, or record that `+crt-static` is necessary (CAP-50a build notes).
5. **Tail segment length, #283:** the requirements must set the PTT VAD segment length that the
   tail budget assumes (CAP-52 says only the tail decodes after key-up; R2 / CAP-19a give only the
   session 15-20 s target). Until then the tail result is CONDITIONAL. Handy's chunker (below) cuts
   at 30 s targets, which would make the tail the whole utterance for most PTT holds.
6. **transcribe-cpp comparison (not done here):** time Handy's engine, `transcribe-cpp` 0.4.2 with
   the Parakeet TDT 0.6B v3 GGUF (`handy-computer/parakeet-tdt-0.6b-v3-gguf`), on the same clips.
   It was not cheap in this run: `transcribe-cpp` builds native transcribe.cpp/ggml code, Handy's
   `BUILD.md` lists CMake as a build tool, and CMake is not installed on this Mac
   (`cmake: command not found`). Installing tools is out of scope for this spike, and the GGUF model
   is a second download. sherpa-onnx stays the pass/fail subject (CAP-48, D78).

## Patterns to reuse from Handy for SttEngine (#45)

Handy (`cjpais/Handy`, MIT, commit `aca8985`) was read only. No Handy code is copied into this PR.
Handy uses `transcribe-cpp`; Bottle keeps sherpa-onnx (CAP-48). The patterns below fit #45:

- **Preload at key-down (CAP-51c):** `actions.rs` calls `TranscriptionManager::initiate_model_load`
  when recording starts, and preloads the VAD on a second thread. `initiate_model_load`
  (`managers/transcription.rs`) is idempotent: a mutex flag `is_loading` plus a condvar, so a
  second key-down neither starts a second load nor blocks; the transcribe call waits on the condvar.
  On load failure it raises a notice only for dictation.
- **Model residency with an idle unload:** an idle-watcher thread unloads the model after
  `model_unload_timeout` (Never, Immediately, 2/5/10/15 min, 1 h; default 5 min). Every load,
  recording and decode calls `touch_activity()`, and the watcher never unloads while a recording or
  file job is active. This maps to D78 ("resident on AC, unload after 30 min on battery"): reuse
  the watcher and add the power-source rule.
- **Worker supervision (`engine_supervisor/`):** all native inference runs in a child process (the
  app binary started with a hidden `--transcribe-worker` flag) that one `EngineSupervisor` owner
  thread controls through a framed stdin/stdout protocol and a command queue. A native abort or hang
  kills only the worker. The supervisor keeps the `LoadSpec` and starts a new worker with the same
  model, so callers never see the restart. Deadlines scale with the audio length (a floor plus a
  multiple of the audio seconds), so a slow CPU is not taken for a hang. At most one worker holds a
  model, and the worker lives exactly as long as the model, so an unload returns all its memory to
  the OS. That last point also matters for NFR-05 (#282): the 1.9 GB of onnxruntime memory is freed
  only when the process that holds it exits.
- **Chunked decode during speech (CAP-52):** `managers/transcription/chunked.rs` with
  `audio_toolkit/chunking.rs` cuts audio at Silero VAD pauses as it arrives and decodes each chunk
  once its cut is certain, "so a recording has only its last chunk left when it stops". Handy's
  targets are 30 s chunks (5 s minimum, 40 s maximum), so its tail is often the whole utterance; a
  Bottle PTT rule needs shorter segments for the tail budget (#283).
