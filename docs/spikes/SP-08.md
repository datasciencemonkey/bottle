## Method

The probe `sp08-probe` opens the default input device with cpal. It runs each mode K times. Each run prints
timestamped events (`[t=... ms] mode=... run=... event=...`) and one `RUN` line. Each mode prints one `SUMMARY`
line with min, p50, p95 and max (nearest-rank).

| Mode | Steps in one run | What it shows |
|---|---|---|
| `build-only` | Build the input stream. Never call `play()`. Hold it `--hold` s. Drop it. | Does a built stream alone turn the device (and the indicator) on? |
| `build-then-play` | Build. Wait `--wait` s. Simulated key-down, then `play()`. Hold. Drop. | CAP-21 path. Latency with a pre-built stream. |
| `build-pause-then-play` | Build, then `pause()` at once. Wait. Key-down, then `play()`. Hold. Drop. | Same as above for a host that starts the stream at build. |
| `cold` | Key-down. Build, then `play()`. Hold. Drop. | The SP-08 fallback (stream built at key-down). |

- **Cached device in every mode**: the probe gets the default input device and `default_input_config()` once,
  before the first run (`probe()` in `src/main.rs`). Each run only builds (and plays). So `cold` already is the
  "cache the device and config at start" path. `--mode all` runs `cold` last, so the device is warm.

- **Key-down to live mic** is the time from the simulated key-down mark to the first input callback after
  that mark. Both marks use one monotonic clock (`Instant`). A callback before key-down does not count as live.
- **The numbers are a lower bound** for CAP-21 and NFR-02 in the app. "Key-down" is a timestamp that the
  control thread takes right before `play()` (or before the build in `cold`). It does not include the hotkey
  delivery, the thread or IPC hop into CaptureService, or a lock wait. The first callback as "live" is a
  conservative end mark.
- **Callbacks before play**: the probe counts callbacks that come before key-down. More than 0 means the stream
  is live before `play()`.
- **Non-zero audio**: the probe records only one bit per run: "a sample was not 0". All zeros on macOS can mean
  that the Microphone permission is missing. The probe does not log or store audio.
- **CoreAudio flags (macOS only, supporting evidence)**: the probe reads two flags of the default input device
  through `AudioObjectGetPropertyData`. It reads them before the build, at 50 ms intervals while it waits or
  holds, and 300 ms after the drop. The flags are:
  - `kAudioDevicePropertyDeviceIsRunningSomewhere` (`gone`): some process runs IO on the device. The OS
    indicator follows device use, so this flag is the closest automated signal.
  - `kAudioDevicePropertyDeviceIsRunning` (`goin`): this process runs IO on the device. Expected (not shown
    by the probe): another app that uses the mic does not change this flag.
  Each `RUN` line shows them as `somewhere/here`. It also shows two verdicts (`evidence_somewhere`,
  `evidence_here`): `IdleUntilPlay`, `LiveBeforePlay` or `Inconclusive` (for example when another app already
  uses the mic at the baseline).
- **cpal source check (0.18.2, macOS)**: `build_input_stream` calls `AudioUnitInitialize` and sets
  `playing: false`. Only `play()` calls `AudioOutputUnitStart`. So on macOS the build does not start IO.
- **Windows**: the same crate is cfg-clean for `x86_64-pc-windows-msvc`
  (`cargo clippy --all-targets --target x86_64-pc-windows-msvc -- -D warnings` passes on the Mac). The
  CoreAudio flags are `n/a` off macOS (`TODO(#15)` in `src/main.rs`); on Windows the person reads the
  CapabilityAccessManager registry (steps below). I did not link or run a Windows binary.
- **Prior art**: Handy (`cjpais/Handy` @ aca8985, `src-tauri/src/managers/audio.rs`) has two mic modes,
  `AlwaysOn` (open the mic at start) and `OnDemand` (open it at key-down). It also waits for a "first sample"
  readiness signal. These match `build-only`/`build-then-play` and `cold` here, and the first-callback mark.
  Handy's cpal code is in the separate `handy-recorder` crate, which is not in the reference copy. No Handy code
  is copied into this spike.

$last = ''

  Get-ChildItem $key | Where-Object PSChildName -like '*sp08-probe.exe' | ForEach-Object {

}

## Pass rule

The SP-08 criterion is only "indicator off until `play()`" (SP-08 row). SP-08 passes on an OS when, on that OS:

1. In M1/W2 the person sees no indicator for the full hold, and the probe reports `cb_total=0`.
2. In M2/W3 (or M3/W4) the indicator stays off until `event=play` and comes on after it.

If step 1 or 2 fails on an OS, SP-08 fails on that OS.

The latency targets are separate requirements. They do not change the SP-08 result:

- **CAP-21** (p95 ≤ 60 ms with a pre-built stream, from M5/W5): if SP-08 passes and CAP-21 also passes,
  CaptureService pre-builds the stream. If SP-08 passes and CAP-21 fails, CaptureService still pre-builds the
  stream (it is faster than `cold` and keeps the indicator off). Record the measured p95 and open a follow-up
  issue to change the CAP-21 target or to find a faster start.
- **NFR-02** (p95 ≤ 150 ms): applies to the path that the OS uses. If SP-08 fails on an OS, the `cold` p95 from
  M5/W5 is the NFR-02 result on that OS. If it is over 150 ms, NFR-02 fails there; open a follow-up issue.

## Fallback

If SP-08 fails on an OS, CaptureService builds the input stream at key-down on that OS (the `cold` mode).
The NFR-02 target is then p95 ≤ 150 ms. CAP-21 does not apply on that OS.

## CAP-21 implications

- On macOS, cpal 0.18.2 `build_input_stream` sets the hardware format first: `set_physical_format` (bit depth
  and sample rate), or `set_sample_rate` if that fails (`src/host/coreaudio/macos/device.rs`). So a stream
  that the app pre-builds at start changes the format of the input device for every app on the system, while
  the mic indicator is off. To avoid a change, CaptureService can build with the device's current format (as the
  probe does with `default_input_config()`). A person can check this in Audio MIDI Setup before and after M1.
- A pre-built stream is bound to one device (Follow-up 3).

## Follow-ups

1. **Cold path margin (NFR-02 at risk):** `cold` p95 was 150.1 ms in 10 runs on an M3 Max (93.5 ms in the
   3-run refresh). The run already reuses a cached device and config, so caching gives nothing more. The cold
   latency is the build (17-104 ms) + `play()` (31-78 ms, `AudioOutputUnitStart`) + one buffer (about 10 ms).
   A smaller fixed buffer size can cut only the last part (a few ms). The only known large lever is to
   pre-build the stream (CAP-21), which SP-08 decides. If SP-08 fails and M5 shows `cold` p95 > 150 ms, NFR-02
   fails on that OS: open a follow-up issue.
2. **CAP-21 margin:** `play()` alone costs about 33 ms on macOS. `build-then-play` had one 88 ms run. If M5 shows
   p95 > 60 ms, compare `build-then-play` and `build-pause-then-play`, and record the better one in CAP-21.
3. **Device change:** a pre-built stream is bound to one device. When the default input device changes, or a
   device is lost (section 7.2, "Device lost" row), CaptureService must drop and rebuild the stream. This needs a
   test in the CaptureService issue.
4. **Bluetooth:** M6 checks whether building a stream on a Bluetooth headset switches it to the call profile.
   If it does, build at key-down for Bluetooth inputs only.
5. **Windows automation:** a test could read the CapabilityAccessManager key from the probe. `TODO(#15)` marks
   this gap in `src/main.rs`.
