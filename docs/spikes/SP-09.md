## Method

1. Protocol facts come from the public MCP spec, Streamable HTTP transport, protocol 2025-06-18:
   <https://modelcontextprotocol.io/specification/2025-06-18/basic/transports> (read 2026-11-15).
   - Each JSON-RPC message is one POST. `Accept` lists `application/json` and `text/event-stream`.
   - The server replies with one JSON object or with an SSE stream. The client must read both.
   - The server can set `Mcp-Session-Id` on the `initialize` reply. The client sends it on each later request.
   - A 404 on a request with a session ID means the session ended. The client must initialise again.
   - The client sends `MCP-Protocol-Version: 2025-06-18` on each request after `initialize`.
   - A notification gets 202 with no body.
2. Genie One facts come from the Databricks docs page for the Genie One MCP server:
   <https://docs.databricks.com/aws/en/agents/mcp-tools/genie-mcp> (read 2026-11-15), and from
   `research/connector-spec-2026-11-14.md`.
   - URL `https://<host>/ai-gateway/mcp-services/system.ai.genie_one_mcp?o=<workspace_id>`, Bearer token.
   - Tools `genie_ask`, `genie_poll_response`, `genie_get_query_result`, `genie_cancel_response` (and `view_ask` for MCP Apps clients).
   - The page gives no formal JSON schemas. The page does not say how Genie asks for clarification.
3. Live facts from earlier work: the probe of 2026-11-14 (`research/message-board.md`, D56) saw the busy text
   "asking Genie failed: OneChat stream closed before response.created event. Retry may succeed." with no 409.
   That probe did not record the envelope form (JSON-RPC `error` or `isError`).
4. I built a thin client on `reqwest` 0.13 with `rustls` (no `rmcp`, G-04a) and a fake Genie One server on
   `wiremock` 0.6. The tests run the client and the full probe flow against the fake server.
5. No Databricks host was called. No CLI profile was used. The only CLI call was `databricks auth token --help`
   and `databricks auth login --help` (local help text, CLI v1.25.0) to confirm `--force-refresh` and `--scopes`.

### Design

| Part | File | What it does |
|---|---|---|
| Endpoint | `src/endpoint.rs` | Builds the G-02 URL. Rejects `/api/2.0/mcp/genie` (G-03, with "end of life 2026-11-30" in the error), the per-space MCP, the Genie One API SSE, plain `http`, other paths and a missing or non-digit `o=`. |
| Tokens | `src/token.rs` | `TokenSource` trait. `CliTokenSource` runs `databricks auth token --profile <p> --output json [--force-refresh]` and reads `access_token`. The token stays in memory. `Token` has no `Display` or `Serialize`; `Debug` prints `Token(<redacted>)`. A CLI failure keeps only the exit code and a fixed class (`login_required`, `not_u2m`, `profile_not_found`, `timeout`, `other`); the CLI text is dropped, because it can name the host, the workspace ID or the profile. `scrub` is a second guard for log text (tokens in `key:value`, `key=value`, JSON, tabs; hosts; long IDs). `RotatingTokens` is the test double. |
| Transport | `src/transport.rs` | `McpClient`: `initialize` (2025-06-18), `notifications/initialized`, `tools/list` (follows `nextCursor`), `tools/call`. Reads JSON and SSE replies. Asks the token source for each POST (G-04d). One forced refresh and one resend on 401. One new `initialize` on 404 with a session (G-05a); `GENIE_ONE_OFF` on 404 without a session (G-05b). `RATE_LIMITED` with `Retry-After` on 429. No redirects. Only the four Genie tools (G-06a). The trace has no token, body or session ID. |
| SSE | `src/sse.rs` | WHATWG event-stream parse: CRLF, LF or a bare CR, comments, multi-line `data:`. It picks the message whose `id` matches the request; it skips notifications before it. |
| Envelopes | `src/envelope.rs` | `ToolCallOutcome::{Ok, ToolError, RpcError}` keeps a JSON-RPC `error` apart from a `result` with `isError: true`. `SignalRules` (loaded from `fixtures/signals.json`) gives `ConversationBusy` (with the rule ID and the source) and `Clarify`. |
| Contract | `src/contract.rs` | Request builders for every tool call, and a small JSON Schema check (`required`, property types, unknown properties) of these builders against a `tools/list` result. |
| Probe | `src/probe.rs`, `src/bin/live.rs` | The live harness. See "Person steps". |
| Report redaction | `src/shape.rs`, `src/transport.rs` | Default deny. No `serde_json::Value` from the server goes into the report; only typed facts do. `Shape` keeps types, string lengths, array lengths and key counts. A key name shows only at a fixed protocol path (the `CallToolResult` keys, and the top-level Genie One poll keys from a fixed list), and the name then comes from that list. Every other key shows as `key_len` only. Protocol words come from fixed lists: the envelope kind, `isError`, the MCP content types, the poll `status` (else `<other>`), and tool names (`KNOWN_TOOLS`, else a count and lengths). Server metadata is reduced: `serverInfo.name` to a length, a non-2025-06-18 `protocolVersion` to a date (only if `YYYY-MM-DD`) and a length, `Retry-After` to seconds, `http_date` or `invalid`, a JSON-RPC code to an integer or nothing, the content type to a fixed word, and a contract violation to fixed argument and type words or `<name len=N>`. |

### Busy and clarify rules are data

`fixtures/signals.json` holds the rules. Change the data after the live run. Do not hard-code new texts.

- `busy[]`: `{id, contains, sources}`. `contains` is a case-insensitive substring. `sources` is any of
  `json_rpc_error`, `is_error`, `http_body`. Today: `"stream closed before response.created"` in all three.
- `clarify`: the G-22 rule. Status `completed`, `final_answer` shorter than 400 chars, ends with `?`, no
  `query_items`. `explicit_fields` is empty today. If the live run shows a field that names a follow-up
  question, add its name there. An explicit field wins over the heuristic.

`envelope` on `busy_ask` is `is_error` or `json_rpc_error` (or `http_error`); that is the fact the live run records.

Exit code 0 means PASS. Exit code 2 means the run finished but a pass item is not met (verdict `NOT YET` or `NOT PROVEN`). Exit code 1 means a setup error
(for example a bad host or profile name). The `http` list after each step shows every status code, including a
401 and its forced resend if the server rejected a token.

### Pass rule

PASS (`pass_rule.verdict` = `PASS`) when all three hold in `pass_rule` of the report:
- `token_refresh_mid_session` = `pass`: `--force-refresh` gave a new token (`token_changed_after_force_refresh` = true)
  and the next call succeeds on the same session. If the call works but the token did not change, the value is
  `not_proven` and the verdict is `NOT PROVEN`: run the probe again later (for example after 10 minutes). If it
  stays the same, record it; the CLI then does not rotate on demand, and rotation must be shown at a real expiry.
  If `--force-refresh` itself fails (`token_changed_after_force_refresh` = null), the value is `fail`, even when the
  next call works with the cached token. Check the `force_refresh` step error class (for example `login_required`).
- `busy_envelope_recorded`: the busy ask matched a busy rule; `busy_envelope.envelope` names the form.
- `contract_matches_live_tools_list`: no contract violation against the live `tools/list`, and step 5 passes.

The clarify step is a record, not a pass item (G-22 is an S row). If `poll_clarify_to_end` is not `ok`, record
the `keys` and `shape` and update `fixtures/signals.json` (`explicit_fields` or the heuristic).

### Fallback

If the call after a forced refresh fails while a new session works, the live service binds the token to the
session. Then use the fallback of SP-09: recreate the transport (an `rmcp` transport or this client with a new
`initialize`) after each refresh. Record it in an ADR and change G-04d.
