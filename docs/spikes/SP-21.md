MEM-21a gap: sqlite-vec 0.1.9 has **no float16 element type** (only float32, int8 and bit).
A 256-d f16 vec0 index therefore does not exist. The f32 vec0 index is 53.6 MB, which is over the 25 MB limit.
The int8 vec0 index is 14.3 MB, which is under it. Note that a raw f16 copy of 50k x 256 is itself 25.6 MB
(24.4 MiB), so "f16 in ≤ 25 MB" passes only if MB means MiB. Recommendation below.

## Recommended configuration (for the MEM work packages)

1. rusqlite 0.42 with `bundled-sqlcipher-vendored-openssl`, plus the `sqlite-vec` 0.1.9 crate, linked statically
   and registered with `sqlite3_auto_extension`.
2. Index: `vec0(embedding int8[256] distance_metric=l2, embedding_model text partition key)`.
   Keep the f16 vector in a BLOB column on the item row (the "f16 cache").
3. Query: int8 KNN for 5 x k candidates, then exact cosine re-rank on their f16 rows (`knn_int8_rerank`).
   This gives recall@10 0.9995, p95 4.7 ms (k=10) and 11.8 ms (k=50), with a 14.3 MB index.
4. `PRAGMA cache_size = -65536` (64 MiB) or at least enough to hold the index. SQLCipher turns mmap off, so
   each page that is not in the page cache is decrypted on every query (see "page cache" rows).
5. Build sqlite-vec with `-DSQLITE_VEC_ENABLE_NEON` on Apple silicon (`spikes/sp-21/.cargo/config.toml`).
   The crate's `build.rs` does not set it.
6. Warm the index once at app start (one dummy KNN). The cold first query costs 19 ms (int8) to 73 ms (f32).

Why each choice:
- **L2 instead of cosine**: the vectors are L2-normalised (MEM-19b), so `|a-b|^2 = 2 - 2cos` and the ranking is the same.
  sqlite-vec 0.1.9 has NEON code for L2 but a scalar loop for cosine: 12.1 ms vs 2.9 ms p95 (f32, k=10).
- **Partition key instead of metadata column** for `embedding_model` (MEM-20b): the metadata filter cost
  about 15 ms per query (28.5 ms vs 12.1 ms p95, cosine). A partition key filters for free.
- **vendored OpenSSL instead of plain `bundled-sqlcipher`**: `libsqlite3-sys` 0.40 `build.rs` links a system
  `libcrypto` dylib if it finds one (for example Homebrew OpenSSL) and uses CommonCrypto only if it finds none.
  That makes the crypto provider depend on the build machine, and a Homebrew dylib breaks a hardened, library-validated
  app. With the vendored feature, `PRAGMA cipher_provider` returns `openssl`, and `otool -L` shows only
  `libSystem` and `libiconv`. A CommonCrypto build is possible with `bundled-sqlcipher` on a machine with no
  OpenSSL; we did not choose it because the result depends on the machine.

## Method

- Crate `spikes/sp-21/`: `src/lib.rs` (store, outbox, replay, recall), `src/bin/bench.rs` (bench and crash helper),
  `tests/sp21.rs` (six `sp_21_*` tests), `bench.sh` (the full measurement run), `Cargo.lock` committed.
- Store: one SQLCipher 4 file, raw 256-bit key (`PRAGMA key = "x'<64 hex>'"`, no PBKDF2; the app keeps a random
  key in the keychain, MEM-08b), WAL, `secure_delete = ON`, `synchronous = NORMAL`.
- Tables: `items(id, mog_id, text, embedding_model, emb_f16 BLOB)`, `outbox(id, kind, item_id, status, attempts)`,
  `item_vec` (vec0, rowid = item id).
- Embedder: deterministic test double (`TestEmbedder`): a SplitMix64 Gaussian vector seeded by FNV-1a of the text,
  L2-normalised. It has an online/offline switch. No Databricks call.
- Offline write (MEM-10a, MEM-19d): the item row and its `embed` outbox job go in one transaction.
- Replay: FIFO batches of 100. Embeddings are fetched outside the write transaction. Then one transaction per batch:
  `DELETE FROM item_vec WHERE rowid=?`, `INSERT` the vector, write the f16 cache, mark the job `done`.
  Delete-then-insert by rowid makes each job idempotent (at-least-once delivery is safe).
- Crash: `bench replay-crash <db> 100 437` calls `process::exit(3)` right after row 437 is written, inside the
  open transaction of batch 5. The test reopens the file and checks that the open batch rolled back.
- Audit: counts of items, pending jobs, vec rows, distinct vec rowids and f16 rows, plus FNV-1a checksums of
  (rowid, stored bytes) for the vec0 rows and the f16 rows. These are compared with the checksums of what the
  embedder produces for every `done` item.
- Bench data: 50,000 random unit vectors at 256-d (seed 42), inserted in transactions of 1,000 rows. Queries:
  random unit vectors (other seeds). Random Gaussian vectors are a worst case for int8 recall; real embeddings
  cluster and usually quantise better. vec0 is an exact (brute-force) scan, so latency does not depend on the data.
- Latency: `std::time::Instant` around one `knn()` call (prepared statement cached). "Cold" is the first query in a
  fresh process (empty SQLCipher page cache, so every index page is decrypted; the OS file cache is warm).
  A true cold-disk read was not measured: `purge` needs sudo.
- Peak RSS: `/usr/bin/time -l` ("maximum resident set size").
- Percentiles: nearest rank over 1,000 queries.

### Fallback: brute-force cosine over the f16 cache (Rust, `half` crate)

| k | cache load (50k rows from SQLCipher) | first query | p50 | p95 | p99 | peak RSS |
|---|---|---|---|---|---|---|
| 10 | 89.7 ms | 7.44 ms | 7.35 ms | **8.88 ms** | 9.01 ms | 68.9 MB |
| 50 | 57.8 ms | 8.65 ms | 7.42 ms | **8.11 ms** | 8.86 ms | 68.9 MB |

This is a plain scalar loop (`f16::to_f32() * q`); it is not tuned. On M1 expect about 1.5x to 2x these times. It is
still well under 50 ms. The fallback is therefore a real option if a later sqlite-vec release breaks the build.

## Follow-ups

1. MEM-21a wording: sqlite-vec has no f16 type. Proposed text: "LocalStore must keep Qwen3 vectors in `sqlite-vec` as
   256-d int8 with an f16 re-rank copy. The vec0 index fits in 25 MB or less at 50k items." The f16 copy is 25.6 MB
   on its own; state whether the limit covers it.
2. MEM work package: set `cache_size` to hold the vec0 index (about 16 MiB for int8 at 50k) and warm it at start.
3. MEM work package: use a partition key for `embedding_model`, not a metadata column (MEM-20b).
4. Build: carry `CFLAGS_aarch64_apple_darwin=-DSQLITE_VEC_ENABLE_NEON` into the app's `.cargo/config.toml` [env],
   and `bundled-sqlcipher-vendored-openssl` into `mog-core`.
5. Supply chain: pin `sqlcipher-src` and repeat the byte check against the SQLCipher GitHub tag on each upgrade.
